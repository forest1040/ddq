# P4-009 書き込み経路監査

2026-10-14、最初の監査はbb87551のソースを対象とし、同日追加した[共有coordinator](phase4_disk_coordination_implementation.md)の差分も反映した。これはソース上の書き込み経路の監査であり、すべての経路を障害注入テストで実行したという意味ではない。以下で「予約済み」とは、明記がない限り永続的な `DiskBudget` token を指す。token は容量の事前計上であり、書き込みを強制的に制限するガードそのものではない。

## 回復時の互換性と cut の安全性

通常の token 利用者は `reserve → materialize (該当する場合) → release` の順に処理する。`DiskBudget.allocation` と catalog／extent callback の cleanup は、引き続き冪等な `release` を使う。明示的な障害回復は `reconcile` を使い、現在は terminal row の二重 reconcile を拒否する。その後の明示的な `release` で、quiescent cleanup として reconcile 済み行を削除することはできるが、`reserved_bytes` やすでに観測した file bytes は変更しない。既存 call site は `reconcile` を呼ばないため、以前の繰り返しを許容する動作には依存していない。

ledger の `reconcile` API は意図的に完全な recovery protocol ではない。`evidence` field は呼び出し側が渡す長さ制限付きテキストであり、PID の生存、lease の期限切れ、hot-journal recovery、segment inventory、未完了 I/O の停止、prepare／decision records、authoritative cut を検証しない。監査対象の writer 群には、古い予約を自動走査して reconcile する経路がない。回復時は inventory に存在する bytes を保持し、結果が不確かな場合は予約を active のまま残す必要がある。PID の再利用や経過時間だけでは token を解放する根拠にならない。

Catalog／checkpoint の処理には有用な cut 保護がある。`CatalogConnection` は SQL transaction の失敗を rollback し、journal rollback は protected cursor の切り詰めを拒否する。Version 4 の distributed checkpoint は fsync 済み global decision を authoritative とし、decision-copy 配布が失敗してもそれを取り消さない。これらの保護があっても、segment 書き込み、journal 書き込み、catalog 行が一つの原子的な予約になるわけではない。allocator 更新、segment write／fsync、version 公開、journal 追記、prepare、global decision fsync、decision-copy 配布の間でプロセス異常終了を注入する障害試験が必要であり、decision 前の旧 cut と decision 後の新 cut を確認する必要がある。

## VFS の識別情報と機能の証拠

[SQLiteGuard](../src/svsim/catalog_admission.py#L30) は、検出した `sqlite3ext.h` を使い `sqlite_budget_vfs.c` から loadable extension を build し、Python の `sqlite3.Connection.enable_load_extension` 経由でロードする。C extension は SQLite extension dispatch pointer を使い、その status 関数はロード元ライブラリの `sqlite3_libversion()` を返す。[CatalogConnection](../src/svsim/catalog_admission.py#L107) はその version string と `sqlite3.sqlite_version` を比較する。quota-backed store では native guard が利用可能であることを要求する。本番モードの `DiskBudget` も guard 経由で ledger を開き、page limit を読み戻す。

これが示すのは SQLite version string の一致と VFS の利用可能性であり、SQLite build fingerprint の一致ではない。`SQLiteGuard.source_hash` はメモリ内で計算されるが、admission status に含まれず catalog に永続化もされない。選択された header path／hash、compiler identity／flags、ロード済み extension binary hash、SQLite compile options、runtime version は capability tuple として記録されない。将来 strict-capability を検査するには、`SQLiteGuard` の build／load 時と connection status でこれらを取得し、不一致を拒否したうえで、対象 connection の `max_page_count`、journal／temp 拒否、上限超過書き込みの挙動を検証する必要がある。現在のコードは Python と header の build configuration が同一であることを証明しない。

## `strict_capacity_guarantee` が false の理由

ledger と管理対象 catalog には明示的な上限があるが、監査した namespace にはソフトウェアだけの予約と未予約の writer が残る。State segment、journal、trace、payload、JSON sidecar、asset、export が、書き込み／truncate を強制する単一の VFS をすべて共有するわけではない。通常 cleanup では操作単位の token を解放し、異常終了時には保守的に残せるものの、すべての token record が inventory および authoritative-cut recovery 手順に結び付いているわけではない。同じledgerに登録したdataset／suffixは合算調停するが、異なるledgerや外部jobまで自動調停しない。`statvfs`／quota の観測値は外部 job、filesystem metadata、無関係な process、システム動作によって変わり得る。現在の capability／status field は適切に `strict_capacity_guarantee: false` を報告する。
