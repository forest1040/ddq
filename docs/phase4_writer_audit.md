# P4-009 書き込み経路監査

2026-10-14、最初の監査はbb87551のソースを対象とし、同日追加した[共有coordinator](phase4_disk_coordination_implementation.md)と[writer永続化境界](phase4_writer_durability_implementation.md)の差分も反映した。これはソース上の書き込み経路の監査であり、すべての経路を障害注入テストで実行したという意味ではない。以下で「予約済み」とは、明記がない限り永続的な `DiskBudget` token を指す。token は容量の事前計上であり、書き込みを強制的に制限するガードそのものではない。

## 回復時の互換性と cut の安全性

通常の token 利用者は `reserve → materialize (該当する場合) → release` の順に処理する。`DiskBudget.allocation` と catalog／extent callback の cleanup は、引き続き冪等な `release` を使う。明示的な障害回復は `reconcile` を使い、現在は terminal row の二重 reconcile を拒否する。その後の明示的な `release` で、quiescent cleanup として reconcile 済み行を削除することはできるが、`reserved_bytes` やすでに観測した file bytes は変更しない。既存 call site は `reconcile` を呼ばないため、以前の繰り返しを許容する動作には依存していない。

ledger の `reconcile` API は意図的に完全な recovery protocol ではない。`evidence` field は呼び出し側が渡す長さ制限付きテキストであり、PID の生存、lease の期限切れ、hot-journal recovery、segment inventory、未完了 I/O の停止、prepare／decision records、authoritative cut を検証しない。監査対象の writer 群には、古い予約を自動走査して reconcile する経路がない。回復時は inventory に存在する bytes を保持し、結果が不確かな場合は予約を active のまま残す必要がある。PID の再利用や経過時間だけでは token を解放する根拠にならない。

Catalog／checkpoint の処理には有用な cut 保護がある。`CatalogConnection` は SQL transaction の失敗を rollback し、journal rollback は protected cursor の切り詰めを拒否する。Version 4 の distributed checkpoint は fsync 済み global decision を authoritative とし、decision-copy 配布が失敗してもそれを取り消さない。これらの保護があっても、segment 書き込み、journal 書き込み、catalog 行が一つの原子的な予約になるわけではない。allocator 更新、segment write／fsync、version 公開、journal 追記、prepare、global decision fsync、decision-copy 配布の間でプロセス異常終了を注入する障害試験が必要であり、decision 前の旧 cut とdecision後の新 cutを確認する必要がある。

## 限定的なcheckpoint sidecar回収

[設計](phase4_checkpoint_recovery_design.md)と[実装](phase4_checkpoint_recovery_implementation.md)で、P4-009 checkpoint JSON writerが作るintentに限定した明示offline recoveryを追加した。最新committed v4 global decisionとowner prepare、read-only catalogのsemantic metadata、committed journal prefix、root/device/inode、generation-bound target/temp inventoryをrank vote前に検査する。通常runtimeのshared leaseが残るとkernel exclusive leaseを取得できない。dry runが既定で、適用時はexact reservation/link CASとcanonical evidence receiptをtokenごとのSQLite transactionで保存する。

これは全rank・全tokenのdistributed atomic transactionではない。rank vote後の適用中断では一部tokenがterminalになり得る。partial temporaryは削除・truncateせず、prepare/global decisionの必須targetがない場合はactive tokenを残す。decision-copy targetは欠損を許し、partial tempがあれば観測byteをmaterialized accountingへ加えてRECONCILEDにし、proofに残す。通常resume/restoreは欠けたdecision-copyを再作成し、recovery後のpartial tempを削除・cleanupしない。振幅payloadや全physical closureを確認せず、unlinked/uncommitted reservation、extent、catalog/journal、payload、trace、asset、export writerは回収しない。適用は同一persistent ledgerを共有するnode-local volumeに限る。dry runもrecovery-only openを使い、schema migration/create、root登録、shared policy変更を行わない。reservation精算とreceipt保存はapply時だけ行う。recovery-only poolはlogical quota/pending/drainを除外する一方、min_free、未割当pool、native page/journal capを保つ。hot sidefile、schema/policy/root mismatch、pool不足、実I/O errorは拒否する。

## VFS の識別情報と機能の証拠

[SQLiteGuard](../src/svsim/catalog_admission.py#L30) は、検出した `sqlite3ext.h` を使い `sqlite_budget_vfs.c` から loadable extension を build し、Python の `sqlite3.Connection.enable_load_extension` 経由でロードする。C extension は SQLite extension dispatch pointer を使い、その status 関数はロード元ライブラリの `sqlite3_libversion()` を返す。[CatalogConnection](../src/svsim/catalog_admission.py#L107) はその version string と `sqlite3.sqlite_version` を比較する。quota-backed store では native guard が利用可能であることを要求する。本番モードの `DiskBudget` も guard 経由で ledger を開き、page limit を読み戻す。

[writer永続化境界の補強](phase4_writer_durability_implementation.md)で、source／両header／binary hash、header directory、compiler identity／flags、header version／source ID、dispatch runtime version／source ID／compile optionsをcapabilityへ記録した。build入力の変更とload前のbinary変更を拒否し、各connectionのruntimeとdispatch identityを照合する。識別不一致をoptional soft fallbackで受け入れない。catalog settingsへcreationとlatest openを別々に保存し、catalog／ledger statusにも返す。これはconnectionとextension dispatchの一致であり、Pythonとheaderのbuild configuration全体が同一であるとの証明ではない。headerとruntimeのversion差だけでは互換性を拒否しない。

## `strict_capacity_guarantee` が false の理由

ledger と管理対象 catalog には明示的な上限があるが、監査した namespace にはソフトウェアだけの予約と未予約の writer が残る。State segment、journal、trace、payload、JSON sidecar、asset、export が、書き込み／truncate を強制する単一の VFS をすべて共有するわけではない。新しいrecoveryはcheckpoint sidecar intentの一部だけをcutとinventoryへ結び付け、全writerのtoken recoveryは行わない。同じledgerに登録したdataset／suffixは合算調停するが、異なるledgerや外部jobまで自動調停しない。`statvfs`／quota の観測値は外部 job、filesystem metadata、無関係な process、システム動作によって変わり得る。recovery-only poolも実hardware ENOSPCや電源断耐久性を封じない。現在の capability／status field は適切に `strict_capacity_guarantee: false` を報告する。GC、別ledger／外部jobの調停、cross-host、電源断耐久性は未受入であり、P4-009とPhase 4は未完了である。
